# 第 1 章 开局：选路、硬件与预算

> 本章代码：[`code/ch01-getting-started/smoke_test.py`](../code/ch01-getting-started/smoke_test.py)
> 预计耗时：30–60 分钟（含装环境）｜硬件要求：任何能装 PyTorch 的机器

## 1.1 本章目标

动手做完本章，你应该能：

1. 说清手上这台机器**能训多大的模型**、该走哪条主线（小模型 / 大模型）；
2. 跑通本书第一个脚本 `smoke_test.py`，亲眼看到自己设备的训练吞吐与显存占用；
3. 知道两条主线项目（MiniMind / nanochat）各自的定位与依赖方式；
4. 避开环境搭建阶段最常见的 8 个坑。

**前置条件**：Python ≥ 3.10（本书脚本最低支持 3.9）、可联网安装依赖、约 10GB 磁盘空间。

**验收标准**：见 [1.6](#16-验收标准)，跑完脚本并填好那张自测表即算通过。

## 1.2 先看清自己的牌

LLM 实操的第一个问题不是「代码怎么写」，而是「我的设备能干什么」。只看三件事：

| 指标 | 怎么看 | 为什么关键 |
| --- | --- | --- |
| 有没有 GPU | `nvidia-smi`（N 卡）／系统信息（Apple Silicon） | 决定是能训练，还是只能验证流程 |
| 显存多大 | 同上 | 直接决定可训参数量上限（估算公式见 [附录 B](appendix-b-hardware-cost.md)） |
| 自购还是租卡 | — | 决定成本口径：按折旧算，还是按小时算 |

```bash
nvidia-smi                                              # NVIDIA：看型号与显存
python3 -c "import platform; print(platform.machine())" # Apple Silicon 输出 arm64
```

> [附录 B](appendix-b-hardware-cost.md) 给出了完整的硬件档位与成本对照表。本章脚本的价值就是**用你机器的实测值去校准那张表**。

## 1.3 实操：跑通第一个 smoke test

### 步骤 1 · 建一个干净的 Python 环境

```bash
cd code/ch01-getting-started
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
python -m pip install -U pip
```

为什么必须用虚拟环境：LLM 生态的依赖冲突极其频繁（尤其 CUDA 相关包），环境隔离是最便宜的保险。

### 步骤 2 · 安装 PyTorch（务必照官方矩阵选版本）

```bash
# macOS（Apple Silicon，走 MPS 后端）
pip install torch

# Linux / Windows + NVIDIA CUDA 12.4
pip install torch --index-url https://download.pytorch.org/whl/cu124
```

> ⚠️ 不要凭记忆写版本号。到 PyTorch 官网安装矩阵里选与**你的驱动**匹配的那一行，**原样复制**它给的命令。装错版本是本章第一大坑（见 P-002、P-008）。

### 步骤 3 · 运行压测脚本

```bash
python smoke_test.py                            # 默认按 64M 参数压测
python smoke_test.py --target-m 350 --depth 24  # 想试更大规模（层数要一起加）
```

脚本做什么：**不训练真实数据**，而是搭一个与真实模型同构、规模可调的迷你 GPT，跑若干步「前向 + 反向 + 参数更新」，测出单步耗时、吞吐与峰值显存，再外推「跑完 X 亿 token 要多久、多少钱」。

预期输出（**【示意】非实测值**，你的数字会不同；若标 `【实测】` 则须附硬件与版本，规则见 [章节模板](../chapter-template.md) 第三节）：

```text
==============================================================
环境自检
==============================================================
  Python   : 3.12.4
  PyTorch  : 2.5.1
  设备     : cuda  (NVIDIA GeForce RTX 4090)
  显存     : 24.0 GB
--------------------------------------------------------------
测试模型（与真实模型同构，仅规模缩小）
  目标参数量 : 64M
  实际参数量 : 69.0M
  层数 / 宽度: 8 / 576（9 头，每头 64 维）
  词表大小   : 32000（词嵌入+输出头约占 53% 参数）
--------------------------------------------------------------
  [预热] step  1  loss=10.412    412 ms  峰值显存=1.31 GB
  [计时] step  3  loss=10.398    388 ms  峰值显存=1.34 GB
==============================================================
结果
==============================================================
  单步耗时 : 391 ms（5 步均值，已排除预热）
  训练吞吐 : 10,486 tokens/s
  峰值显存 : 1.34 GB
  10 亿 token : 约 26.49 小时，按 $3/小时 约 $79.47
--------------------------------------------------------------
  判断：24GB 显存，小模型全参或 1–3B 级 LoRA 都可行。
```

### 步骤 4 · 读懂输出，做出选路决策

只看四个数：

| 输出项 | 含义 | 怎么用 |
| --- | --- | --- |
| 实际参数量 | 本次压测的模型规模 | 与 `--target-m` 偏差过大，说明参数被词表吃掉了（见下方提示） |
| 训练吞吐 | tokens/s | 乘上你的 token 预算 → 得到小时数 |
| 峰值显存 | 训练态占用 | 必须小于你的显存，并留 20% 余量给波动 |
| 词嵌入占比 | 词表带来的参数占比 | **小模型的关键陷阱**，见下 |

> 💡 **小模型的第一课**：词表越大，嵌入越贵。上例中 64M 模型有 **53% 的参数花在词嵌入和输出头上**，真正做计算的 Transformer 块占不到一半。所以小模型应当**缩小词表**（第 2 章展开）——这是小模型与大模型在工程取舍上的第一个分岔。
>
> 另一个相关现象：把 `--target-m` 调大而 `--depth` 不动，解出来的宽度会大得不合理。例如目标 350M、`--depth 8` 会得到宽度 1600 的「矮胖」模型；把 `--depth` 提到 24，宽度落到 1024，才是常见比例。**「深度是主旋钮」**正是 nanochat 用 `--depth` 单参数配置整条模型系列的思路。

## 1.4 两条主线：定位与版本锁定

选好路线后，把对应项目拉下来。但先记住一条铁律（已升格为全书通则，见 [章节模板](../chapter-template.md) 第五节）：**任何上游项目的命令，都要与版本一起记录。**

| 主线 | 适合谁 | 获取方式 |
| --- | --- | --- |
| MiniMind | 个人显卡；想几小时内看到完整结果 | `git clone https://github.com/jingyaogong/minimind.git` |
| nanochat | 单机多卡；想走 GPT-2 级完整流程 | `git clone https://github.com/karpathy/nanochat.git` |

```bash
git clone https://github.com/jingyaogong/minimind.git
git clone https://github.com/karpathy/nanochat.git

# 关键一步：记录并锁定 commit，避免上游更新导致书中命令失效
cd nanochat
git log -1 --format="%H %ci" | tee ../nanochat.version.txt
```

> 本书后续涉及上游项目时，都会标明**写作时实测通过的版本（commit）**。你动手时若发现命令对不上，先回退到该版本再排查——这一招能排除掉一大半所谓的「环境问题」。
>
> 各项目当前的依赖安装方式以其仓库 README 为准（nanochat 用 `uv` 管理依赖，MiniMind 提供自己的依赖清单）。本书不复制它们的 README，而是给出**带版本的可复现步骤**。

## 1.5 坑点与解法

### P-001｜训练一开始就 OOM（显存不足）

- **现象**：`torch.OutOfMemoryError: CUDA out of memory`，或进程被系统直接杀掉。
- **可能原因**：批太大、序列太长、未开混合精度、词表过大、卡上有别的进程占显存。
- **排查步骤**：① `nvidia-smi` 确认有无其他进程占卡；② 用 `smoke_test.py` 逐步调小 `--batch` / `--seq` 找阈值；③ 确认是否启用了 bf16/fp16；④ 用 [附录 B](appendix-b-hardware-cost.md) 的公式估算理论占用，与实际值对比。
- **解决办法**：开混合精度 → 减小 batch → 缩短序列 → 用梯度累积补回等效批大小 → 开梯度检查点 → 最后才考虑换卡或租云卡。
- **如何预防**：真实训练前，先用 `smoke_test.py` 压测出「你的显存能扛的 batch × seq」组合。

### P-002｜CUDA 版本与 PyTorch 不匹配

- **现象**：`ImportError: libcudart.so...` / `CUDA error: no kernel image is available`，或 `torch.cuda.is_available()` 返回 `False`。
- **可能原因**：装的 wheel 与驱动/CUDA 版本不对应；或本机 CUDA Toolkit 与 PyTorch 自带的运行时不匹配。
- **排查步骤**：① `nvidia-smi` 看驱动支持的 CUDA 上限；② `python -c "import torch; print(torch.version.cuda)"` 看 PyTorch 编译时的 CUDA 版本；③ 两者对照。
- **解决办法**：按 PyTorch 官网矩阵重装对应 wheel（必要时先 `pip uninstall torch`）。
- **如何预防**：永远从官网矩阵**复制**安装命令，不凭记忆手写版本号；把装好的版本记进实验记录。

### P-003｜Apple Silicon 上 MPS 报错或算子不支持

- **现象**：`NotImplementedError: The operator 'aten::xxx' is not currently implemented for the MPS device`，或结果异常。
- **可能原因**：部分算子在 MPS 后端尚未实现；或精度行为与 CUDA 不同。
- **排查步骤**：① 用 `PYTORCH_ENABLE_MPS_FALLBACK=1` 运行，看是否回退成功；② 定位是哪个算子触发。
- **解决办法**：设环境变量允许回退到 CPU；或把该段逻辑放到 CPU 上算；实在不行改用云端 CUDA 跑该阶段。
- **如何预防**：Apple Silicon 上优先选用已验证支持 MPS 的模型实现，并在小步数上先跑通再放大。

### P-004｜显存估算与实际差很多

- **现象**：按「参数量 × 字节数」估的显存够用，实际却 OOM（或反之）。
- **可能原因**：漏算了激活值（随 `batch × 序列长度 × 层数` 增长）、优化器状态、临时缓冲与碎片。
- **排查步骤**：① 用 `smoke_test.py` 拿到实际峰值；② 与公式估算对比；③ 逐个变量（batch / seq）做单变量扫描，看显存增长斜率。
- **解决办法**：按经验系数（约 18–20 字节/参数）重估，并为激活值预留余量；必要时降 batch、开梯度检查点。
- **如何预防**：把「参数量估算」只当作下界，永远以实测峰值 + 20% 余量作为安全线。

### P-005｜云上 spot / 竞价实例被抢占

- **现象**：训练中途进程突然消失，任务被中断。
- **可能原因**：spot 实例被回收（价格上浮或资源紧张）。
- **排查步骤**：① 看云厂商的实例状态与回收通知；② 检查最近一次检查点的时间戳，确认丢了多少进度。
- **解决办法**：从最近的检查点续训；把检查点间隔缩短（spot 场景建议 10–15 分钟一次）。
- **如何预防**：用 spot 省钱的前提是**检查点足够密**，并把检查点写到持久化存储而不是实例本地盘。

### P-006｜吞吐远低于预期

- **现象**：`smoke_test.py` 或真实训练报出的 tokens/s 明显低于同类硬件的公开值。
- **可能原因**：数据加载成为瓶颈（`num_workers` 太小）、未开混合精度、未用融合优化器、通信开销大（多卡）、PCIe/网络带宽不足。
- **排查步骤**：① 先跑纯计算压测（`smoke_test.py`）确认硬件上限；② 再跑真实训练，对比差距；③ 逐项开关（混合精度 / workers / 编译优化）做对比。
- **解决办法**：提高数据加载并发、开 `torch.compile` 或融合注意力、多卡时减少同步频率。
- **如何预防**：把「硬件上限」与「实际吞吐」分开测——两者的差距就是工程优化空间。

### P-007｜结果不可复现

- **现象**：同样的配置跑两遍，loss 曲线不一致。
- **可能原因**：随机种子未固定、数据顺序未固定、多卡归约顺序非确定、cuDNN 自动调优。
- **排查步骤**：① 检查是否设置了 `torch.manual_seed`；② 检查 DataLoader 的 shuffle 与 worker 种子；③ 对比单卡与多卡结果。
- **解决办法**：固定所有随机源；必要时开启确定性模式（会牺牲一些速度）。
- **如何预防**：把「种子 + 版本 + 配置」一起记录进实验记录，缺一不可。

### P-008｜装到的 PyTorch 是 CPU 版

- **现象**：`torch.cuda.is_available()` 为 `False`，但机器明明有 N 卡。
- **可能原因**：用默认源 `pip install torch` 装到了 CPU-only 构建（常见于 Linux 默认源）。
- **排查步骤**：① `python -c "import torch; print(torch.version.cuda)"`，输出 `None` 即为 CPU 版；② 检查安装命令是否带了 `--index-url`。
- **解决办法**：卸载后按官网矩阵重装 CUDA 版。
- **如何预防**：把安装命令原样抄进实验记录，并在装完立刻验证 `torch.cuda.is_available()`。

## 1.7 本章小结与下一步

- 选路的第一依据是**实测**，不是硬件参数表：`smoke_test.py` 给出的 tokens/s 与显存，才是你做预算的基数。
- 小模型的第一课是**词表成本**：64M 模型里可能过半参数花在嵌入上，这直接决定第 2 章分词器怎么选。
- 上游项目必须**锁版本**——这是「可复现」三个字的落点。
- 下一章进入数据与分词：从原始语料到能喂给模型的训练集。
