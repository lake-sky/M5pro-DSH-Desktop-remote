# 案例：AI 写小说 skill 调研任务的流式超时

- **日期**：2026-10-02
- **任务**：调研开源社区「AI 写小说 skill」→ 在 `study/skills/` 下建立调研区 → 写 5 篇文档（README、ecosystem、projects、deep-dives、takeaways）→ 更新各级索引并提交
- **症状**：写到第 4 篇（`deep-dives.md`，计划中最大的一篇）时中断，报错：
  `[重试延迟：8709 毫秒 / 失败原因：pi-ai stream idle timeout after 300000ms]`
  即模型流超过 5 分钟无输出，harness 重试一次后仍失败。
- **失败时进度**：README.md / ecosystem.md / projects.md 已落盘；deep-dives.md、takeaways.md、索引更新、git 提交均未完成（且 3 篇已完成文档也未提交，全部处于 untracked 状态）。

## 原因分析

1. **主因：上下文过长**。调研过程中把 7 个仓库的 README（合计约 80KB）与网页抓取结果（含一次 51KB 的截断 JSON 溢出文件）读进了对话并逐篇通读。上下文越重，预填充与逐 token 生成越慢，流式闲置超过 300 秒被判定超时。
2. **诱因：单次大输出**。`deep-dives.md` 是体量最大的一篇（7 个项目深度剖析），原计划一次写完；「重上下文 + 大输出」叠加，生成时间越过 5 分钟阈值。
3. **结构性因素：没有检查点**。todo 里把「提交」放在最后一步，已完成的 3 篇没有及时 commit，进度只存在于磁盘、不存在于版本历史，恢复时缺少可靠的「做到哪了」依据。
4. **补充发现：子代理外包同样不稳定**。恢复阶段两次尝试把剩余两篇文档交给子代理执行（新上下文、自己读源文件、自己写文件），两次均以 `subagent run failed` 结束（第二次有部分输出后中断）。说明在本环境/该时段，模型流稳定性问题不是主会话独有；**恢复策略必须以「本地分段直写」为兜底**，不能依赖子代理成功。

## 处置

1. 盘点现场：`find` + `git status` 确认 3 篇已落盘、2 篇缺失、全部未提交；`/tmp/sr` 的调研源文件仍在。
2. 子代理两次失败后**停止重试**，改为主会话分段写入：`deep-dives.md` 用「1 次写入 + 3 次追加」共 4 段完成（148 行）；`takeaways.md` 用「1 次写入 + 1 次追加」完成（40 行）。每段均控制在约 2–3KB。
3. 更新 `study/README.md`（新增「技能研究」分类与索引条目）与 `novelist/README.md`，清理临时目录 `.research-tmp/`。
4. 提交：`9b79bae docs: 新增 AI 写小说 skill 调研（生态/项目全景/深度剖析/共性模式）`。

## 教训（已并入 SKILL.md）

- 大文件必须分段写；重活优先外包、外包失败立即回退分段直写。
- 大数据先落盘，后续定点取用，不整篇重读。
- 每个交付物完成即提交，让进度存在于 git 而不是只存在于磁盘。
- 识别信号：单文件 > 4KB、单次抓取 > 10KB、交付物 > 5 个、会话已出现重试——命中即启动预防。
