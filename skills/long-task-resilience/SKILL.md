# long-task-resilience（长任务抗超时与恢复）

## 何时适用

- 单轮要写出较大的文件（> 约 4KB）或大量结构化内容
- 会话里已经灌入大量资料（网页正文、API JSON、大文件全文）
- 一个任务有多个交付物，无法一次做完

## 识别信号（出现即开始预防）

| 信号 | 含义 |
| --- | --- |
| 单个文件需要连续输出 > 4KB | 流式中断概率显著上升 |
| 某次 `web_fetch` / `read` 返回 > 10KB | 上下文正在变重 |
| 单个任务交付物 > 5 个 | 必须拆分 |
| 本次会话已出现过一次慢响应或重试 | 已接近阈值 |

## 预防（按顺序执行）

1. **大文件分段写**：先用 `write` 写第一部分，其余部分用追加方式（`bash` heredoc `cat >> file <<'EOF'` 或 `edit`）分多次完成；单次工具调用新增内容 ≤ 约 4KB。
2. **重活外包**：大批量「资料阅读 + 文档装配」交给子代理（全新上下文）——子代理自己读源文件、自己写文件，主会话只收摘要。⚠️ 若子代理机制本身不可用（连续失败），立即回退到第 1 条的分段写入，不要反复重试子代理。
3. **大数据先落盘**：`web_fetch` 返回大结果后，立刻把关键内容存成本地文件（或依赖溢出文件），后续用 `grep` + `read`（带 offset/limit）定点取用，不要整篇重读进上下文。
4. **每个交付物即时提交**：一个文件写完就 `git commit` 一次，小步提交不丢人；`todo` 列表同步更新。
5. **开工前先估算拆分**：先列出交付物清单与大致体量，拆成「多个小步、每步可提交」的单元再动手。

## 恢复（已发生超时/失败时）

1. **不要盲目重试同样的巨型输出**。先查磁盘现状：`ls` / `read` 看实际落盘到哪一步，`git status` + `git log` 看已提交什么。
2. **不要从零重写**：半成品用定点追加补齐；源材料若仍在磁盘（临时目录/溢出文件），从源材料重建，而不是凭记忆重敲。
3. **重建任务状态**：看 todo 清单 + git log 判断「已完成 / 未完成」，然后按上面的预防策略继续。
4. **记录案例**：在对应 skill 目录写一份案例（命名 `YYYY-MM-DD-<摘要>.md`），把新发现的原因补进本文件的预防清单。

## 反模式（不要做）

- 上下文已经很重时，还用单次调用写 10KB+ 的文件
- 失败后把已经落盘的内容重新生成一遍
- 把中间调研材料全部塞进主对话
- 只在任务最后提交一次（全有或全无），中途失败就一无所有
