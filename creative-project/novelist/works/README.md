# works（作品区）

**一部作品一个独立目录。** 这是本工作区唯一的创作产出区，[../study/](../study/) 与 [../publishing/](../publishing/) 都为它服务。

## 为什么改成「一部作品一个目录」

早期做法是把所有正文平铺在一个 `chapters/` 下。作品一多必然出现两个问题：

1. **混**——三部作品的第 3 章都叫 `003-xxx.md`，靠文件名分不清谁是谁；
2. **丢**——改稿时直接覆盖原文件，想找回上一版只能翻 git；一旦不是技术操作，就彻底丢了。

改为一作品一目录后：作品内部的大纲、人物、正文、草稿、笔记各自有位置，**改一部作品不会影响其他作品**。

## 目录约定

```text
works/
└── <类型>-<序号>-<英文短名>/     # 如 short-001-three-minutes/
    ├── README.md                # 作品档案：简介、状态、版本记录表、目录说明
    ├── outline.md               # 大纲（活文档）
    ├── characters.md            # 人物设定（活文档）
    ├── chapters/                # 正文：一章一文件，只放正文
    │   └── NNN-<英文短名>.md
    ├── drafts/                  # 历史版本与废弃稿（只归档，不删除）
    └── notes.md                 # 创作笔记、技法对照、实验记录
```

- **作品目录命名**：`<类型>-<序号>-<英文短名>`。类型取 `short`（短篇）/ `novel`（长篇）/ `serial`（连载）；
- **目录名一经创建不再改名**——改名会让所有引用失效；
- **只建用得到的子目录**，不要预先铺满空目录（唯一例外是 `drafts/`，它需要有个明确的位置放归档）。

## 版本规划（本体系的核心）

### 三层版本，各司其职

| 层级 | 场景 | 谁负责 | 怎么做 |
| --- | --- | --- | --- |
| **行级** | 改字、改句、调段落 | **git** | 直接改 `chapters/` 里的文件，**不要手动复制版本文件** |
| **章级** | 整章重写、推翻重来 | **人工归档** | 重写前把旧版复制到 `drafts/`，命名 `YYYY-MM-DD-<原文件名>-v<N>.md` |
| **作品级** | 里程碑（开篇完成、初稿、定稿） | **作品 README 的版本表 + git tag** | 见下 |

> **为什么要这样分工**：git 擅长行级历史，但它表达不了「这是我第三稿」这种语义；反过来，如果每一稿都手动存文件，目录会迅速堆满 `v1`/`v2`/`v3` 而无法阅读。
> **结论：行级交给 git，章级和作品级交给人。不要用人工归档去做 git 已经做好的事。**

### 作品级版本号

- 格式 `v<主>.<次>`：`v0.x` = 未完成阶段；`v1.0` = 定稿；
- 每次到达里程碑，在**作品 README 的版本记录表**加一行，并打一个 git tag：

```bash
git tag short-001-three-minutes/v0.1
git push --tags
```

tag 命名规则：`<作品目录名>/v<版本号>`。

### 章节文件四条规则

1. **一章一文件**，命名 `NNN-<英文短名>.md`（`NNN` 为三位章号，如 `001-opening.md`）；
2. **章号一经分配不再复用**——删掉某章时文件移入 `drafts/` 而不是真删，章号作废、不回收；
3. **正文文件里只放正文**。创作笔记、技法对照、灵感碎片一律放 `notes.md`——这样 `chapters/` 里每个文件都是「可以直接拿去发布」的状态；
4. **插入新章用小数或后缀**（如 `002a-xxx.md`），**不要重排后面章号**——重排会让所有引用和历史记录错位。
