# 共性模式与对我们的启示

把 16+ 个项目的做法横向对比后，能提炼出一套反复出现的工程化共识。下面先列模式，再落到我们自己的 novelist/study 该怎么用。

## 一、十条共性模式

1. **文件系统当记忆**。设定、大纲、正文、追踪拆成独立目录各自维护，对话只负责创作、不负责记忆。几百章的长篇不靠对话历史硬撑，上下文压缩也不丢线索。
2. **单一真相源 + 派生视图**。结构化文件（如 `_tracking-state.json`）是唯一权威，上下文卡、伏笔视图、角色状态都由它重新渲染；手改派生文件会被校验拒绝。这样避免了多份状态互相打架。
3. **「作者真相 / 读者已知」分离**。作者知道的设定与读者已经看到的信息分账记录。这是「角色提前知道答案」「伏笔写飞」的主要根治手段，也是 oh-story 反复强调的设计。
4. **流程门禁（gate）**。无细纲不许写正文（硬拦截）、字数用机器口径统一、完稿必须过一致性复查。把质量控制前移成前置条件，而不是写崩了再返工。
5. **确定性脚本 vs 模型判断分工**。能机器判定的交给脚本：句式 lint、字数统计、截断检测、结构校验；只有「读感」这类主观判断留给模型与作者。去 AI 味因此变成可复现的 lint 而不是玄学。
6. **动态状态回写**。每完成一章就回写：关键事件、人物状态、关系变化、情节线推进、伏笔状态、世界规则变更、情绪债务与未兑现承诺、下一章承接压力。状态不会静默消失。
7. **模块化按需加载**。主 `SKILL.md` 短、稳、可维护，只做路由与全局原则；具体知识下沉到 `references/` 按需读取。避免一个巨型 prompt 同时兼顾开头、转场、对白、审查，最后全部变钝。
8. **多 Agent 分工 + 模式选择**。架构、正文、一致性、检索各设专职 Agent；写作模式按需在串行 / 子 Agent 并行 / Agent Teams 之间切换，速度与稳定性可权衡。
9. **拆文库 + 语料检索**。把爆款或有代表性的作品拆成情节节点、情绪类型与强度、写作手法，配上正例反例与来源索引，形成可检索的模块库。流程是「先匹配素材，再构思，再写作」。
10. **人在回路（human-in-the-loop）**。从空瓶分块陪写、粗稿待精修，到明确主张「AI 现阶段不宜直出」的陪练派——成熟项目普遍把作者放在定稿位置，而不是让 AI 一步到位。

| 低（下一步） | 本地 clone `oh-story-claudecode` 与 `Novel-Control-Station-Skill` 两仓库精读（均为 MIT），各提炼 3–5 条方法论要点 | `study/technique/` |

补充说明：`study/skills/`（本目录）只负责**调研与索引**，方法论正文应沉淀到 `technique/`、素材清单沉淀到 `material/`、名家文风沉淀到 `author-styles/`，避免调研报告越写越厚却无法在写作时调用。

## 三、注意事项与风险

- **star 数 ≠ 质量**。高 star 多来自传播度与完整度；方法论深度要看 `references/` 文档本身。生态迭代极快（版本号从 0.2.x 到 0.8.x 混布），跟随时以仓库为准。
- **去 AI 味是移动靶**。句式库和检测器都在演化，lint 只能清确定性痕迹，读感判断仍需人；不要把它当成「绕过检测器」的工具。
- **版权边界**。学方法、不抄句子；引用或搬运任何文档前先确认 license（多数为 MIT / Apache-2.0，个别未标注）。
- **区分技法与商业规则**。这批项目大多面向商业网文平台（起点、番茄、晋江），其「黄金三章、爽点密度、追更感」是平台生存规则，与文学写作的目的不同。研读时把可迁移的叙事技法与不可迁移的商业套路严格分开——本目录的剖析已尽量按此标准区分。
- **工具依赖风险**。多数 skill 依赖特定 Agent 宿主（Claude Code / Codex 等）与本地脚本，跨环境迁移需要验证；本工作区使用的 DeepSeek Harness 已有 oh-story-dsh 社区插件，可作为后续实测入口。
